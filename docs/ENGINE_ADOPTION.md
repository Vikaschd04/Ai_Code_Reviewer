# Engine adoption and licensing

Adopt engines through replaceable adapters. Read the original research appendix only when making an adoption decision; it is not a startup instruction file. Its 25 September 2026 findings are a baseline, not a perpetual license or API guarantee.

For every selected version record: upstream URL; release/commit and image digest; runtime requirements; supported language versions; scope/exclusion behavior; command/output contract; exit-code semantics; cancellation; rulepack origin/license; transitive dependencies; telemetry/network behavior; config execution; release provenance; maintenance status; fixtures and benchmark results.

Initial priority: PMD/CPD and ESLint, then Opengrep with approved rules and Trivy; Salesforce Code Analyzer for the Salesforce pack; evaluate Alibaba OCR for AI. Verify exact distributions before shipping. A process boundary is not a legal exemption.

Semgrep-maintained rules, Sonar analyzers/data interactions, CodeQL entitlements and OpenRewrite modules/recipes have distinct terms. Do not assume top-level engine licensing covers everything. If rights are unclear, implement against an owned/cleared rule or alternate engine and document the limitation; do not present restricted functionality as included.

Pin tools and prevent automatic source-specified plugin/config execution. If executable project config is supported, put it in an explicit sandboxed mode. Contract-test path/line encodings, partial/error reporting and output compatibility. Keep raw reports and provenance while publishing normalized findings.

Use docs/playbooks/ENGINE_ADOPTION.md for the adoption workflow. No current scanner/tool is installed by this documentation kit.
