# Phase roadmap

All phases start NOT_STARTED. Timing is a planning reference for a dedicated team, not a coding-session promise. This upload-first sequence supersedes the original research's GitHub-first intake assumption; retain its engine/evidence/security recommendations.

| Phase | Target | Depends on | Planning window |
|---|---|---|---|
| 0 | Working web/API/DB/workflow foundation and docs | Specification | Weeks 1–2 |
| 1 | ZIP/local-folder capture, inventory, PMD/ESLint baseline and dashboard | 0 | Weeks 3–6 |
| 2 | Persistent graph, more scanners, exports and lifecycle | 1 | Weeks 7–12 |
| 3 | Bounded AI investigation and usage controls | 2 | Weeks 13–16 |
| 4 | SAP Commerce/Salesforce domain packs | 2; 3 for AI enhancements | Weeks 17–20 |
| 5 | Validated patch workflow and download | 3–4 | Weeks 21–24 |
| 6 | GitHub and incremental/PR workflows | 2 and 5 for publication | Weeks 25–28 |
| 7 | Qualified enterprise release | Applicable earlier gates | Weeks 29–36 |

Each phase prompt specifies implementation, tests and evidence. Security, authorization and source isolation begin in Phase 0/1. Phase 7 matures them; it does not introduce basic protection for the first time.

No phase requires claiming every language/framework scenario is covered. A phase can finish its defined conditional-capability handling while a specific platform test remains unavailable, but that capability cannot be called verified. Mandatory gate failures keep the phase open.

First usable release = Phase 1. Full framework-aware AI repair product = Phases 1–5. GitHub is an optional later input/publication channel, not a hidden dependency of non-Git analysis.
