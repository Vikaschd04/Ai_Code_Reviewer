# ADR 0008 — Snapshot graph, issue lifecycle, comparison and per-file cache

Status: accepted and implemented, 27 September 2026 (P02). Owner: development agent for the repository maintainer.

Context: P02 requires snapshot-versioned mappings with evidence and classifications, bounded graph/impact queries, cross-scan issue lifecycle where absence in a partial or incompatible scan is not "resolved", comparison, exports, and caching keyed by content plus parser/rule/config scope.

Decision:

- **Graph builds per snapshot** (`graph_builds`, `graph_nodes`, `graph_edges`, migration 0003). A pseudo-engine `graph` in each scan extracts per-file facts with Tree-sitter (package, declared types, imports/re-exports/require/dynamic import, extends/implements, import bindings) and resolves them snapshot-wide. Each edge stores source evidence (file, lines, normalized line text), extractor id and a classification: `resolved` (deterministic: Java FQN index and import rules, relative paths with TS/Node extension rules including `.js`→`.ts`, `tsconfig` `paths`/`baseUrl`, workspace package names, Maven module coordinates), `declared` (external but consistent with a declaration: JDK packages, Node built-ins, manifest dependencies), `inferred` (heuristics such as Maven groupId prefix → Java package) or `unresolved` (reason recorded). Composite foreign keys force node/edge file anchors to belong to the build's snapshot.
- **No stale links:** one `is_current` build per snapshot (partial unique index). Publishing a build retires the previous one and deletes its nodes/edges in the same transaction. A failed or canceled extraction publishes a FAILED current build, so APIs return "latest build failed" instead of older links. Partial parses keep relations from well-formed regions and mark the file.
- **Bounded APIs:** summary (counts, module dependency aggregation), node search (paged, ≤100), neighborhood (depth ≤2, node limit ≤300, edge cap per level, `truncated` flag), impact (file/module level, depth ≤5, limit ≤500, breadth-first with a visited set; reports unresolved-edge and parse-problem caveats). No endpoint returns a whole graph.
- **Issues** (`issues`, `issue_events`): one durable issue per project fingerprint. `status` (OPEN, TRIAGED, ACCEPTED_RISK, FALSE_POSITIVE, FIX_PROPOSED, RESOLVED) is separate from `recheck_state` (VERIFIED_PRESENT, VERIFIED_ABSENT, NOT_RECHECKED, UNKNOWN, RULE_OBSOLETE). An absent issue is VERIFIED_ABSENT only if the same engine completed, analyzed the same path, still enables the rule, and has the same engine version and rule-set hash as the last observation; only then does OPEN/TRIAGED/FIX_PROPOSED become RESOLVED. Deleted/renamed files → UNKNOWN; failed or unanalyzed files → NOT_RECHECKED; removed rules → RULE_OBSOLETE. Resolved issues reopen when reported again. The lifecycle applies only for scans of the newest evaluated snapshot that completed at least one engine (older-snapshot rescans only link findings). Triage (PATCH with optimistic `version`) may set OPEN/TRIAGED/ACCEPTED_RISK (reason + expiry ≤1 year)/FALSE_POSITIVE (reason); database CHECKs enforce reasons and expiry. Expired exceptions revert to OPEN at the next applied scan and are flagged at read time.
- **Comparison** uses the same classifier for base-vs-target fingerprints and reports per-engine compatibility.
- **Correlation:** `correlation_key` = rule family + path + start line + per-engine occurrence slot on that line. Cross-engine duplicates (e.g. ESLint `no-eval` and Opengrep eval) correlate; distinct occurrences on one line or on different lines never collapse; every engine observation is kept.
- **Per-file cache** (`engine_cache`, project-scoped, cascade-deleted with the project). Key = sha256 of cache version, workspace, project, engine, engine version, rule-set hash, adapter configuration fingerprint, normalization versions (fingerprint, correlation, catalog), materialization limit, path and blob SHA-256. Only files ANALYZED in a SUCCEEDED/PARTIAL run with a matching engine version are stored; failed parses and timeouts are never cached. `cache_mode=refresh` bypasses reads and overwrites. The graph extractor uses the same table as a syntax cache (blob + extractor version); resolution is always recomputed because other files and manifests change it. Engines whose results depend on other files (Trivy) are not cached.
- **Exports:** platform JSON (`crp-scan-export/v1`, JSON Schema 2020-12 shipped in the package) and SARIF 2.1.0 derived from it; engines that did not run appear with `executionSuccessful: false`.

Alternatives considered: a graph database (unnecessary at this scale; Postgres with bounded queries meets the phase); a recursive CTE for impact (explored every path; 427 ms on the benchmark vs 9.8 ms for level-wise BFS); treating absence as resolution (explicitly forbidden); cross-project cache sharing (skipped to keep the tenant boundary simple).

Consequences: graph relations are syntax-level; calls, DI, reflection and types from dependencies are not resolved. The lifecycle follows "newest snapshot wins". A rule/engine upgrade makes absent issues UNKNOWN until triaged or re-observed. Cache entries have no automatic eviction yet (bounded by project deletion; see KNOWN_ISSUES).

Evidence: `packages/analysis/tests/test_graph.py`, `test_lifecycle_reports.py`, `services/worker/tests/test_p02_analysis.py`, `test_engine_cache_keys.py`, `packages/core/tests/test_migrations.py`, docs/validation/P02_REPORT.md.
