# ADR 0011 — refactorX name, demo account, sample project and reviewer-first UI

Status: accepted and implemented, 30 September 2026 (owner request). Owner: development agent for the repository maintainer.

Context: the owner asked to (1) rename the application to **refactorX**, (2) offer a demo login on the sign-in page so people can try the product directly during development, (3) ship a sample project for a dry run, (4) fix UI issues and (5) show users only what they need for code review — technical and configuration details hidden or simplified — as a standing rule for current and future work, because the product targets a global, industry audience.

Decision:

- **Name.** "refactorX" is the user-facing name everywhere (UI, page title, favicon/brand mark, OpenAPI title, SARIF `tool.driver.name`, README and docs). Internal identifiers — Python packages `crp_*`, the `crp-dev` CLI, `CRP_*` settings, database names and the Render resource names `ai-code-reviewer` / `ai-code-reviewer-db` — stay, because renaming them would break existing environments and the free database (one per workspace) without user benefit.
- **Demo account** (`CRP_DEMO_ENABLED`, default off; on in `render.yaml`, Codespaces Compose, local dev and E2E). `POST /v1/auth/demo-session` (allowed Origin required) provisions and signs in the subject `demo:guest` with **member** access to a separate `demo` workspace only; `GET /v1/auth/options` (public) tells the UI whether to offer it. Demo sessions are signed cookies like owner sessions, accepted only while the demo stays enabled, never via the bearer token. Existing workspace-scoped authorization means the demo user cannot see or reach the owner's projects (404), and it is not an operator (no diagnostics or system status). Quotas: `CRP_DEMO_MAX_PROJECTS` (30) and `CRP_DEMO_MAX_SCANS_PER_HOUR` (20) → HTTP 429 `demo_limit_reached`. The UI marks every page with a shared-workspace notice.
- **Sample project.** `POST /v1/projects/sample` creates "Sample: Online store" (origin `synthetic_fixture`, badge "Sample") from files packaged in `crp_api/samples/online_store` and sends a deterministic ZIP through the normal intake path (artifact store → worker validation → frozen snapshot); the UI then starts a review — one click, real engines. The fake access token is generated at runtime (never committed). The sample triggers PMD, ESLint, Opengrep and Trivy findings (asserted in `services/worker/tests/test_sample_project.py`).
- **Reviewer-first UI** (docs/UI_SPEC.md): plain vocabulary (`apps/web/src/lib/labels.ts`), technical provenance in collapsed "Technical details", administration pages for operators only, developer affordances only in local development, visual review of light/dark/mobile screenshots (`apps/web/e2e/ui-tour.spec.ts`). The API contract is unchanged apart from the new endpoints and `is_demo`.

Alternatives considered: a per-visitor demo workspace (true isolation between visitors, but each visitor would need a fresh sample review — minutes of CPU on the free instance — and unbounded rows; revisit with retention in P07); a read-only demo (safer, but the owner asked that visitors can run tests); renaming internal identifiers (breaking, no user value).

Consequences and risks:

- Anyone who can open the URL can use the demo: upload code (≤ 25 MB on Render free), run reviews within the quotas, and **see everything other demo visitors uploaded** (shared workspace; stated on every page). Uploaded code is analysed by the same unsandboxed engines as the owner's (K-P01-01), so a malicious archive targeting an analyzer vulnerability affects the whole single-tenant instance. The demo must be disabled (`CRP_DEMO_ENABLED=false`) before real customer data is stored on the same deployment; P07 brings per-tenant isolation and SSO.
- Demo data has no automatic cleanup yet; it counts against the free database's 1 GB (K-P10-02).
- Quotas are soft (concurrent requests can exceed them slightly).

Evidence: `services/api/tests/test_demo_and_sample.py` (options, disabled/enabled demo, Origin check, isolation from the owner workspace, operator denial, project quota, sample creation through the intake path, unavailable workflow service, cookie invalidation when disabled), `services/worker/tests/test_sample_project.py` (demo user reviews the sample with all real engines; hourly scan quota), `apps/web/e2e/ui-tour.spec.ts` (demo sign-in, one-click sample review, every screen, light/dark/mobile screenshots, no horizontal scroll), updated `foundation`, `p01` and `p02` specs; docs/validation/REFACTORX_UI_REPORT.md.
