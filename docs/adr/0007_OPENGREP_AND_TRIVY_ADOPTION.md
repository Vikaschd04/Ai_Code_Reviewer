# ADR 0007 — Opengrep (owned rules) and Trivy (offline dependencies and secrets)

Status: accepted and implemented, 27 September 2026 (P02). Owner: development agent for the repository maintainer.

Context and constraints: P02 requires pinned Opengrep with owned/approved rules and Trivy after an exact-version license, configuration and security review, run for real on positive and negative examples, with unsupported formats and unavailable databases exposed. Uploaded repositories are untrusted and may contain tool configuration files. In March 2026 Trivy's release pipeline was compromised (GHSA-69fq-xp46-6x23): some published artifacts after 19 March 2026 were malicious.

Decision:

- **Opengrep 1.30.0** (LGPL-2.1, fork of Semgrep CE), official `opengrep_osx_arm64` release binary, SHA-256 `0f5bc3de…89fdd` pinned; optional Sigstore verification with `cosign verify-blob` against identity `https://github.com/opengrep/opengrep/.github/workflows/rolling-release.yml@refs/heads/main` (issuer `token.actions.githubusercontent.com`). Used as an unmodified separate executable; no Opengrep code is linked or redistributed.
- **Rules are platform-owned** (`packages/analysis/src/crp_analysis/rules/opengrep-rules.yml`, ruleset `crp-opengrep-v1`, 10 Java/JS/TS rules written for this project). No Semgrep-registry or third-party rule packs are embedded (their licences differ). Every rule has a catalog entry, a positive fixture and a negative fixture (`fixtures/projects/security-mixed`).
- Opengrep runs with `--disable-nosem` (source comments cannot suppress rules), `--no-git-ignore`, `--disable-version-check`, a per-file timeout, `--max-target-bytes` = the intake text-file limit, and `XDG_CACHE_HOME` inside the engine directory (the binary self-extracts once; without this every run re-extracted into HOME and took 24–39 s). Findings from rule ids outside the owned set are counted as `unknown_rules`, never published.
- **Trivy 0.69.3** (Apache-2.0). Chosen because Aqua listed it as a verified-safe release after the compromise; its Rekor transparency-log timestamp (3 March 2026) predates the attack. SHA-256 `a2f2179a…43a5` pinned for `trivy_0.69.3_macOS-ARM64.tar.gz`; `crp-dev engines --verify-signatures` verifies the Sigstore bundle with identity `https://github.com/aquasecurity/trivy/.github/workflows/reusable-release.yaml@refs/tags/v0.69.3`. Verified in this session with cosign v3.1.3 (both binaries), including a clean reinstall into a scratch directory.
- **Trivy runs fully offline:** `--offline-scan --skip-db-update --skip-java-db-update --disable-telemetry --skip-version-check`, scanners `vuln,secret` only (no misconfiguration or licence scanning, no image/registry access). The vulnerability database is downloaded only by `make engines` (`trivy image --download-db-only`, ~1.3 GB in `.local/engines/trivy-cache`); a missing DB makes the engine UNAVAILABLE with a reason. DB `UpdatedAt` is part of the Trivy rule-set hash, and a stale DB (past `NextUpdate`) is reported in diagnostics and the UI.
- **Repository config cannot change results:** Trivy gets an explicit trusted `--secret-config` (`rules/trivy-secret.yaml`, built-in rules only) and an empty `--ignorefile` written outside the snapshot, so `trivy.yaml`, `.trivyignore` and `trivy-secret.yaml` inside uploads are inert.
- **Secrets are never stored:** Trivy `Match`/`Code` fields are removed before the raw report is persisted; findings carry only rule id, file and line; source excerpts shown in the UI pass through redaction.
- Dependency findings are anchored to the manifest/lockfile (`anchor_kind = dependency`); a line is stored only when Trivy reports one (no invented lines). Findings keep engine severity, the DB's advisory data (installed/fixed version, PURL, status) and guidance marked as coming from the Trivy database.
- Trivy is not cached per file (its results depend on the whole tree and on the DB). Opengrep, PMD and ESLint are cached per file (ADR 0008).

Alternatives considered: Semgrep CE with registry rules (rule licence terms); Trivy latest (post-compromise releases needed individual verification; a pinned, verified release is safer); OSV-Scanner (would need network access or a separate offline DB workflow; can be added behind the same adapter later); Gitleaks for secrets (Trivy already covers the P02 need with one pinned binary).

Consequences: Opengrep coverage is limited to the owned rules (intra-file patterns, no cross-file taint). Trivy results depend on the DB snapshot date; absent vulnerabilities after a DB update are UNKNOWN, not fixed (rules changed). Maven transitive dependencies that need remote parent POMs are not resolved offline. Only macOS arm64 binaries are pinned; other platforms need their own pins. Disk: ~1.3 GB DB plus ~440 MB of engine binaries/cache.

Evidence: `packages/analysis/tests/test_security_engines.py` (real runs, positive/negative, nosem, unavailable DB/binaries), `services/worker/tests/test_p02_analysis.py`, docs/validation/P02_REPORT.md, docs/ENGINE_ADOPTION.md.
